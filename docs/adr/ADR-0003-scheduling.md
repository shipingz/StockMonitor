# ADR-0003: 调度方式 — 收盘后 3 分钟精确对齐（修订版，取代「每 5 分钟轮询」）

- 状态：**已确认**
- 日期：2026-08-15（确认）；2026-08-15 修订（从轮询改为精确对齐）

## 修订记录

- v2（当前）：收盘后 3 分钟精确对齐，16 次/天，无状态（ADR-0005）。
- v1（已废弃）：交易时段每 5 分钟轮询，48 次/天，需要跨运行去重状态。

修订原因：用户在意信号时效性；且参考项目 [ZhuLinsen/daily_stock_analysis](https://github.com/ZhuLinsen/daily_stock_analysis) 的实践表明「低频精确触发 + 无状态」是 GitHub Actions 上更简洁的形态；16 次/天也大幅减少运行次数。

## 背景

GitHub Actions 的 `schedule` cron 支持分钟级精度，但触发不保证准时（高负载时段——每个整点——延迟最严重），且 schedule 触发的运行失败后**不会自动重试**。需要在「时效性」「漏检风险」「状态复杂度」之间权衡。

## 事实约束（已查证）

- cron 最小 5 分钟间隔，但可精确到分钟（如 `3 2 * * 1-5`）。
- schedule 事件在 GitHub 高负载时段（整点）可能延迟数分钟；极端情况超过 15 分钟。
- schedule 运行失败无自动重试 → 该次检查永久丢失。
- 仓库 60 天无 activity，GitHub 会**自动禁用 scheduled workflows**（用户决策：本项目每日有人查看，不做 keepalive，接受此风险；若日后发现被禁用，补一个 keepalive 步骤即可）。
- 公有仓库 Actions 分钟数免费且不限额。
- A股每天 16 根 15 分钟K线（北京时间）：9:45、10:00、…、11:30、13:15、…、15:00。

## 决策

采用 **收盘后 3 分钟精确对齐**，16 个触发时刻全部显式写入 cron（UTC）：

| 北京时间触发 | UTC cron | | 北京时间触发 | UTC cron |
|---|---|---|---|---|
| 9:48 | `48 1 * * 1-5` | | 13:18 | `18 5 * * 1-5` |
| 10:03 | `3 2 * * 1-5` | | 13:33 | `33 5 * * 1-5` |
| 10:18 | `18 2 * * 1-5` | | 13:48 | `48 5 * * 1-5` |
| 10:33 | `33 2 * * 1-5` | | 14:03 | `3 6 * * 1-5` |
| 10:48 | `48 2 * * 1-5` | | 14:18 | `18 6 * * 1-5` |
| 11:03 | `3 3 * * 1-5` | | 14:33 | `33 6 * * 1-5` |
| 11:18 | `18 3 * * 1-5` | | 14:48 | `48 6 * * 1-5` |
| 11:33 | `33 3 * * 1-5` | | 15:03 | `3 7 * * 1-5` |

- 收盘后 3 分钟而非 1 分钟：避开整点延迟尖峰（10:03 的触发点 10:00 是整点，但触发在整点后 3 分钟），并留足排队余量。
- **护栏（健康监测）**：脚本检查「最新已收盘K线」距其收盘时刻是否超过 15 分钟；若超过说明严重延迟或漏检，跳过推送并记录告警日志。
- 节假日剔除：cron 只排周一至周五，法定节假日由脚本内交易日历判断（ADR-0006），非交易日直接退出。
- workflow 同时提供 `workflow_dispatch` 手动触发（含 dry-run 模式）用于测试。
- 不做 keepalive：用户每天查看本项目运行结果，接受 60 天禁用风险。

## 后果

- 每天 16 次运行，单次 30~90 秒，公共仓库额度免费。
- **正常路径无状态**：同一根K线只被一次运行看到，无需跨运行去重（ADR-0005）。
- 已知边界（接受）：
  - 某次运行失败 → 该根K线漏检，无补偿；失败可见于日志。
  - job 延迟跨过K线边界（>12 分钟，罕见）→ 可能偶发重复推送 1 条或漏 1 根K线。
  - 严重延迟（>15 分钟）→ 护栏拦截并告警。
- 参考项目 [daily_stock_analysis](https://github.com/ZhuLinsen/daily_stock_analysis) 采用类似思路：每天一次低频触发 + 进程内降噪、不做跨运行持久化。
